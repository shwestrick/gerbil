# Sandboxing

Every gerbil session runs inside a container. The host never executes a command
the agent wrote. The container engine is Docker by default, or podman when
`GERBIL_SANDBOX=podman`.

## What the agent can see

Into the container go:

- every git-tracked file in the project;
- a **sanitized `.git`** -- a fresh repository holding only the current
  branch's history. No other branches, tags, remotes, upstreams, reflogs, or
  unreachable objects. Whatever else is in your repo, the agent has no path to
  it.
- submodule contents, fully populated (see below);
- the Lean toolchain, `lake`, and the [lean-lsp MCP server](tools.md).

The agent has no host filesystem access at all: gerbil never bind mounts. Files
enter as a tar and leave as `git format-patch` text.

Outbound network access is not itself blocked -- `lake exe cache get` and
toolchain downloads need it -- but the tools that would use it are removed:
the lean-lsp tools backed by external services are filtered out of the
advertised schemas and refused if invoked anyway. See
[Tools](tools.md#disabled-network-tools).

## Mathlib caching

If the Lake project depends on mathlib, gerbil starts every sandbox session
with `lake exe cache get` to pull precompiled oleans -- otherwise the first
build spends hours compiling mathlib from source.

Projects that don't use mathlib skip it automatically. `cache` is an executable
*mathlib itself* provides, so running it elsewhere doesn't merely waste time,
it fails.

Detection reads `lake-manifest.json` -- Lake's *resolved* dependency graph, so
mathlib arriving indirectly through another package still counts -- plus the
`require`s in `lakefile.toml` / `lakefile.lean`, and takes the union (a
manifest is generated by `lake update` and can lag a lakefile that just gained
mathlib). If none of those can be read, gerbil fetches anyway: the skip is only
taken on positive evidence that mathlib is absent.

`gerbil run --skip-cache` suppresses the fetch for a mathlib project too --
faster to start, but mathlib then rebuilds from source on first use.

## Submodules

gerbil supports projects that *use* submodules; the agent does no submodule
manipulation.

Contents are uploaded from the host's already-initialized working tree. Cloning
inside the container would require the `.gitmodules` URLs to be reachable and
their credentials available, and gerbil never writes to the host repo -- so
preflight refuses an uninitialized, moved, or dirty submodule instead of
fixing it for you.

On the way out, every gitlink (and `.gitmodules`) is restored to its base state
before the patch is produced, so no submodule change can reach a patch. This is
enforced rather than merely requested of the agent, because a patch *cannot*
carry submodule work: `format-patch` renders a gitlink as a single
`Subproject commit <sha>` line, the objects behind it die with the container,
and `git am` would happily commit a pointer to a commit that exists nowhere.

## Using your own sandbox image

By default gerbil builds and runs its own image. If your project needs
something that image doesn't carry -- pre-built artifacts, extra system
packages, a pinned toolchain, private tooling -- point gerbil at your own:

```console
$ gerbil run --image my-lean-sandbox:v1 --prompt prompt.md
```

`--image` works with `gerbil run`, `gerbil resume`, and
`gerbil reconstruct-patch`.

### Per-project and per-user configuration

To make an image the default for one project, write it into that project's
`.gerbil/config.toml`:

```toml
image = "my-lean-sandbox:v1"
```

The same keys may also live in a user-level `~/.gerbil/config.toml`, as your
personal defaults across every project; a project's config always overrides
the user's, key by key. (Today the keys are `image` and `theme`, the live
view's color scheme.)

Image selection goes, highest precedence first: `--image`, then the project's
`.gerbil/config.toml`, then `~/.gerbil/config.toml`, then
`GERBIL_SANDBOX_IMAGE`, then `gerbil-lean-sandbox:latest`. The config files
deliberately outrank the environment, because the launcher *always* exports
`GERBIL_SANDBOX_IMAGE` (its version-matched build) -- otherwise a project (or
user) could never state its own image.

The resolved image is recorded in the session log for provenance, but
`gerbil resume` re-resolves rather than reusing it: gerbil's own image tag is
version-pinned, and updating gerbil prunes superseded images, so a recorded
default would go stale the moment you ran `gerbil update`.

### What an image must provide

Your image has to fit how gerbil drives the container, so gerbil checks it at
startup -- before any work -- and refuses with *every* problem listed at once,
rather than failing halfway through a session.

| Requirement | Why |
| --- | --- |
| `sh`, `bash`, `timeout` | every command gerbil runs is `timeout N bash -c CMD` |
| `git`, `tar`, `chown`, `id`, `mktemp` | git plumbing, upload unpacking, post-upload ownership fix, `--ralph_done` |
| `lake` on `PATH` | the mathlib cache fetch and every build |
| a writable `/workspace/project` | gerbil's workspace; podman will not create a missing `--workdir` |
| runs as uid 1000 (or 0) | uploads are tarred as uid 1000 and `chown -R`ed to it |
| root `exec` works | used once after upload to fix ownership |
| no `ENTRYPOINT` swallowing the command | the container runs `sleep infinity` and is driven with `exec` |
| `lean-lsp-mcp` on `PATH` | **optional** -- without it you get a warning and the built-in tools only |

The simplest way to satisfy all of this is to build `FROM` gerbil's own image
(`src/lean-sandbox/Dockerfile`).
